# Plano: papéis de plataforma e console mínimo de contas

- Status: ativo
- Spec associada: [identidade, espaços, permissões e administração](../../specs/identidade-e-administracao.md)

## Objetivo

Entregar ADMIN-001/002 em uma boundary administrativa separada: bootstrap documentado do
primeiro `platform_admin`, autorização server-side por papel de plataforma, proteção do último
administrador, busca por ID/e-mail normalizado, metadados mínimos, suspensão/reativação, sessões e
reenvio pelos fluxos Better Auth.

## Estado inicial

O PWA já possui `/admin` e um shell separado, mas a página de contas é um placeholder. A API só
possui o boundary doméstico de identidade. Better Auth ainda não está configurado com o plugin de
admin nem com os campos `role`/`banned`; a migration DATA-004/0019 ainda não entrou em `main` e a
fatias de cartões reservam a sequência seguinte. Portanto, esta branch prepara contratos, política,
rotas, adapters e testes sem criar migration concorrente; a integração de schema será adicionada
após a coordenação das migrations.

## Abordagem

- Manter papel de plataforma independente de memberships e limitar respostas ao conjunto mínimo de
  metadados permitido pela spec.
- Exigir `platform_admin` no servidor para ações de administração; `platform_support` permanece
  leitura/ações de suporte permitidas e nunca promove outro admin.
- Modelar comandos mutáveis com motivo obrigatório, chave de idempotência, autenticação recente e
  proteção do último admin. A UI usa a API administrativa e não decide autorização.
- Reutilizar Better Auth para sessões, suspensão e envio dos fluxos de verificação/recuperação;
  não implementar tokens ou credenciais paralelos.

## Rastreabilidade

- ADMIN-001: bootstrap, papéis, step-up e último-admin em `admin-policy`/`admin-service` e testes.
- ADMIN-002: listagem/detalhe, sessões, suspensão/reativação e reenvios em `admin-routes` e UI.
- Isolamento: nenhuma consulta recebe `workspaceId` como escopo e respostas não incluem valores,
  descrições, produtos, senha, token ou conteúdo financeiro.

## Riscos

- Sequência de migration pode mudar enquanto DATA-004/CARD são integrados; nenhum arquivo de
  migration desta branch deve ser aplicado antes da coordenação do índice.
- Better Auth possui capacidades de admin próprias; usar as rotas/adapter oficiais evita tokens
  paralelos, mas a política Casei continua sendo validada antes delas.
- Suspensão deve revogar sessões já emitidas e impedir novas sessões; a integração final precisa
  ligar o status persistido ao hook de criação de sessão do Better Auth.
- TOTP/step-up usa o plugin oficial `twoFactor` do Better Auth. A autorização administrativa não
  confia em papel de sessão: a migration coordenada deve adicionar o schema do plugin, o papel
  persistido e o vínculo de autenticação reforçada antes de expor mutações administrativas em
  produção.
